Why CypherLite

CypherLite exists to fill a specific gap: there was no lightweight, embeddable graph database with a Cypher interface and zero configuration. This page explains the motivation, the design trade-offs, and where CypherLite fits alongside other tools.

The gap​

Graph databases are powerful, but most of them require infrastructure:

  • Neo4j — the most popular graph database. Requires a running JVM server, significant memory, and configuration. Excellent for production workloads, but heavy for prototyping, scripting, or embedding.
  • Amazon Neptune, ArangoDB, TigerGraph — cloud or server-based systems that need deployment and administration.
  • DGraph, JanusGraph — distributed graph databases designed for scale, not simplicity.

On the other end, tools like SQLite demonstrated that a database can be a single file opened with a single function call. SQLite is embedded in billions of devices precisely because of this simplicity.

CypherLite brings the SQLite approach to graph data:

PropertySQLiteCypherLite
Data modelRelational (tables)Property graph (nodes + relationships)
Query languageSQLCypher
DeploymentSingle file, zero configDirectory (WAL + snapshot codec), zero config
EmbeddableYes (C library)Yes (Rust crates, Python, C FFI)
Server requiredNoNo

Design goals​

1. Zero configuration​

cypherlite ./mydata
# or: cypherlite --snapshot-format json ./mydata-json

That's it. No config files, no server processes, no ports, no authentication setup. Persistent URIs are directories (WAL + a snapshot codec). If the directory doesn't exist, it's created. If it does, it's opened.

2. Cypher — the graph query language people already know​

Cypher is the most widely adopted graph query language, originally developed for Neo4j and now an open standard via openCypher. By using Cypher, CypherLite is immediately familiar to anyone who has worked with Neo4j or other Cypher-compatible databases.

3. Embeddable​

The storage and engine crates are designed as a library. You can run Cypher queries inside your application without spawning a separate process — from Rust:

use cypherlite::{Database, Value};

let db = Database::open(":memory:").unwrap();
let mut conn = db.connect().unwrap();
let result = conn.query("RETURN 1 + 2 AS sum").unwrap();

…or from Python (built from source with maturin develop) or any language with a C FFI.

4. Graphs that fit in RAM​

The matcher is in-memory (typed CSR). That is a fit for:

  • Prototyping — sketch a graph model without standing up a server.
  • Scripting — query graph-shaped data from the CLI, pipe results.
  • Education — learn Cypher without installing JVM infrastructure.
  • Embedding — Rust, Python, or C FFI without a network dependency.
  • Workloads that fit memory — application graphs, fraud slices, ontologies, knowledge bases.

It is not a clustered Neo4j replacement and not a DuckDB-style warehouse that scans Parquet as the engine. Checkpoint files are for open/replay.

What CypherLite is not​

Being clear about non-goals prevents disappointment:

  • Not a clustered database — one process, one working set in RAM. Durability is a local WAL plus a snapshot directory, not a replicated cluster.
  • Not a warehouse engine — Parquet checkpoints are not scanned by MATCH. There is a MATCH-rewrite planner, not a cost-based columnar executor.
  • Not a multi-user server — no authentication, authorization, or multi-process writers. Bolt is a transport in front of one engine.
  • Not a second Cypher dialect — the floor is the openCypher TCK (strict 3896/3897 with 1 documented skip under the single cypherlite-tck harness). Some Neo4j/CIP features remain stretch work.

The SQLite analogy​

The comparison to SQLite is intentional and pervasive:

FeatureSQLiteCypherLite
Shell promptsqlite>cypher>
Dot-commands.tables, .schema, .dump.help, .begin/.commit/.rollback, .checkpoint (introspect with Cypher)
In-memory mode:memory::memory:
File argumentsqlite3 mydb.dbcypherlite ./mydb (directory)
Pipe executionsqlite3 db < file.sqlcypherlite ./mydb < file.cypher
Output modes.mode csv/json/table-csv / -json / --mode flags

If you know SQLite's workflow, CypherLite will feel natural. The only difference is the data model and query language.

Where it fits​

                        ┌──────────────────┐
                        │  Neo4j / Neptune  │  Production, large-scale
                        │  TigerGraph       │  graphs, enterprise features
                        └──────────────────┘
                                 ▲
                                 │  scale & features
                                 │
              ┌──────────────────┴──────────────────┐
              │           CypherLite                 │  Prototyping, embedding,
              │   lightweight · embeddable · simple  │  scripting, education
              └──────────────────────────────────────┘
                                 ▲
                                 │  graph model
                                 │
                        ┌──────────────────┐
                        │     SQLite        │  Relational data,
                        │  (tables + SQL)   │  embedded SQL
                        └──────────────────┘

CypherLite doesn't replace any of these — it's a new point in the design space where graph data meets zero-infrastructure simplicity.
