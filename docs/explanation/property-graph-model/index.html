Property Graph Model

CypherLite stores data as a labeled property graph. Schema is optional: labels and relationship types do not need DDL. Properties are mixed-type maps (openCypher TCK).

The four building blocks​

1. Nodes​

Nodes represent entities — people, places, products, events.

CREATE (:Person {name: 'Alice', age: 30})

Every node gets a unique integer ID from a process-wide counter. Concurrent creates do not collide.

2. Labels​

Labels are string tags on nodes. A node can have zero, one, or many. Internally they are interned ids in the catalog; Cypher still sees strings.

CREATE (:Person:Employee {name: 'Alice'})

MATCH (n:Person) is a label scan (postings of node ids), not a full graph scan, unless no label is given.

3. Relationships​

Relationships are directed, typed connections between two nodes:

  • Start node and end node (direction matters)
  • Exactly one type (FRIENDS_WITH, ACTED_IN, …)
  • An auto-generated unique ID
CREATE (a)-[:FRIENDS_WITH {since: 2020}]->(b)

Expand uses typed CSR: [:FRIENDS_WITH] walks that type's adjacency chunk only. A bare -[]- visits every type partition.

4. Properties​

Both nodes and relationships carry key-value pairs. Keys are interned; values are TCK types (null, bool, integer, float, string, list, map, temporal, point, geometry, vector, plus nested structures the language allows).

Public Node / Relationship maps (what RETURN n shows) are materialized from compact live records at node_at / rel_at, checkpoint encode, and overlay copy-on-write. They are not the on-heap layout the matcher walks.

How it looks in memory​

The live store is the source of query execution:

catalog     interned labels, rel types, property keys
nodes       compact records (label ids + property list) with xmin/xmax
rels        compact records or a fixed fraud shape (id / amount / ts)
out/in      typed CSR: type_id → Vec<RelId>   (visibility superset)
indexes     label, equality, prefix, trigram postings (also supersets;
            prefix/trigram built lazily on first seek, ADR-0063)

That means:

  • Lookup by id at a snapshot is a versioned node_at / rel_at, not a HashMap of fully built Cypher maps.
  • Outgoing relationships of a type are O(degree of that type).
  • (:Person) is O(count of that label's postings), then visibility filter.
  • Deletes set xmax; they do not rewrite CSR holes. Readers skip dead edges.

MVCC: a reader pins snapshot_ts. A version is visible when xmin <= snapshot_ts && (xmax == 0 || xmax > snapshot_ts). Incremental GC drops versions no pin still needs.

On disk, a checkpoint is Parquet shards or graph.json — a snapshot of committed state, not the structure the expander uses. See Storage Engine.

Comparison with relational data​

Relational:

Table: persons          Table: friendships
| id | name  | age |   | person_a | person_b | since |

Property graph:

(Alice:Person {age:30}) -[:FRIENDS_WITH {since:2020}]-> (Bob:Person {age:28})

A join becomes a hop. Multi-hop stays a path:

MATCH (p:Person {name: 'Alice'})-[:FRIENDS_WITH*2]->(fof)
RETURN fof.name

Schema flexibility​

  • Nodes with the same label need not share properties.
  • SET n:NewLabel / REMOVE n:OldLabel and SET / REMOVE on properties are always allowed (subject to constraints).
  • CREATE INDEX names a (label, property) pair for the catalog; MATCH seeks whether or not that name exists.

For stricter guarantees, use constraints:

CREATE CONSTRAINT required_name
FOR (p:Person) REQUIRE p.name IS NOT NULL;

CREATE CONSTRAINT unique_email
FOR (p:Person) REQUIRE p.email IS UNIQUE;

Uniqueness, existence, type, and node/relationship key constraints are enforced on commit. They persist in the WAL and in the snapshot envelope.

When to use a graph​

Property graphs excel at connected data, variable-depth traversals, mixed entity types, and schema evolution.

They are less suited for warehouse-style scans of data that will not fit in RAM, append-only time series with no edges, or multi-megabyte blobs as properties. CypherLite is an in-memory engine with a WAL — SQLite's shape, not DuckDB's.
