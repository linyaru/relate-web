Query Execution

CypherLite turns a query string into rows with parse → lower → plan → execute. The executor interprets a LogicalPlan against a pinned snapshot of the in-memory graph. It does not walk the parser AST clause-by-clause against a GraphStore.

Parsing pipeline​

1. Lexing​

The lexer (cypherlite-parser) emits tokens:

Input:  MATCH (n:Person) WHERE n.age > 25 RETURN n.name

Tokens: MATCH  (  n  :  Person  )  WHERE  n  .  age  >  25  RETURN  n  .  name

Keywords, identifiers, literals, operators, and punctuation.

2. Parsing​

A hand-written recursive descent parser builds a Cypher AST. Each clause has a dedicated parse function (parseMatch, parseCreate, parseReturn, …). Expressions use precedence climbing (parseOr → parseAnd → … → parseAtom).

3. AST​

A Statement is a list of Clause values. For example:

MATCH (p:Person) WHERE p.age > 25 RETURN p.name
Statement {
  Clauses: [
    MatchClause { pattern: (p:Person), where: p.age > 25 },
    ReturnClause { items: [p.name] }
  ]
}

4. Lowering (cypherlite-front)​

The front-end validates (including relationship uniqueness in a pattern) and lowers the CypherLite AST into planner IR (cypherlite-ir). That IR is what the planner consumes. A historical IR parser exists only for diagnostics (CYPHERLITE_PARSER); it is not the product query path (ADR-0046, ADR-0053).

Planner​

cypherlite-planner binds names against the catalog and emits a LogicalPlan. v1 validates, then rewrites MATCH / OPTIONAL MATCH only. WITH, writes, and UNION keep clause order. There is no cost model and no DataFusion / LLVM backend.

MATCH rewrite, in order:

  1. Fold. Top-level n.k = literal|$param and n:Label on a node introduced in this MATCH merge into that node's map so the first access can be an index seek. Residual WHERE stays on the clause.
  2. Orient. For a connected path with no path variable, if the last node is strictly more selective than the first, reverse the path.
  3. Order. Disconnected comma patterns are stable-sorted by the seed score of each path's first node (bound variable, then label+equality, then label, then bare node).

The executor never rewrites the parser AST; rewrites live only on the plan.

Execution​

Snapshot and overlay​

  • Reads pin snapshot_ts and use MVCC visibility (xmin <= snapshot_ts && (xmax == 0 || xmax > snapshot_ts)). They do not clone the graph.
  • Auto-commit writes run against a private write overlay. MATCH in the same statement sees overlay first, then the snapshot. Success turns the overlay into physical redo, appends the WAL (the serialize point), then apply_redo.
  • Explicit transactions (.begin / BEGIN) hold one pin until .commit / COMMIT or rollback. Nested begin is an error.

Two overlapping writers fail with Error::Conflict (write-write conflict). The engine does not retry.

Pattern matching​

After rewrite, the first node is an equality seek, a label scan, or an all-node scan. Each hop expands the typed CSR partition for that relationship type ([:KNOWS] walks only that chunk; a bare -[]- visits every partition) and checks rel_at visibility.

Residual WHERE conjuncts run as soon as every variable they mention is bound, not only after the full path.

Rows keep only live variables between clauses.

Variable-length paths​

MATCH (a)-[:KNOWS*1..3]->(b)

Bounded expansion from each seed, respecting type and direction. Each valid length produces a row.

Aggregates and expand​

One-hop sum / count (and CASE + count) over a bound node's out-edges can fold while walking adjacency instead of allocating one row per edge. Expand ordered by a relationship property (ORDER BY t.ts) can walk a sorted view of that type's chunk.

Clause pipeline (logical)​

The plan still looks like Cypher's clause sequence. Context rows flow forward:

ClauseRole
MATCHBind nodes/rels via seek, scan, expand
WHEREResidual predicates (also folded into MATCH)
CREATE / MERGE / SET / DELETE / REMOVEOverlay mutations
WITHProject, aggregate, reshape
UNWINDOne row per list element
RETURNFinal columns
CALL {}Per-input-row subquery
CALL proc()Built-in procedures
FOREACHNested mutations
LOAD CSVRows from a file

Expression evaluation​

The executor evaluates plan expressions against the current row and snapshot:

  • Literals, variables, property access, operators, functions, CASE
  • EXISTS {} — inner plan, true if any row
  • List comprehensions and reduce()
  • shortestPath / allShortestPaths — BFS (bidirectional and a shallow hop bound when both ends are bound), not “expand every trail then keep the shortest”

Aggregation​

Non-aggregate expressions form the grouping key. Each group accumulates count, sum, avg, min, max, collect, stDev, then emits one row.

MATCH (p:Person)
RETURN p.city, count(*) AS population, avg(p.age) AS avg_age

Subqueries​

CALL — for each input row, run the inner plan. Outer variables are in scope. The subquery RETURN adds columns.

MATCH (p:Person)
CALL {
  WITH p
  MATCH (p)-[:KNOWS]->(friend)
  RETURN count(friend) AS friendCount
}
RETURN p.name, friendCount;

EXISTS — boolean; true if the inner plan produces a row.

MATCH (p:Person)
WHERE EXISTS { MATCH (p)-[:KNOWS]->(:Person {name: 'Alice'}) }
RETURN p.name;

Indexes (access methods)​

Seeks happen whether or not a named CREATE INDEX exists. Named indexes are catalog entries persisted in the WAL and manifest.json; they do not enable or disable matching.

Access methodUsed for
Label postings(:Person)
Equality map{id: $id}, n.k = $q
Prefix BTreeMapSTARTS WITH
TrigramCONTAINS
Typed CSRrelationship type expand

Postings are a visibility superset; the executor filters by snapshot (and overlay on writes). Prefix and trigram postings are built lazily on the first seek of their (label, property) pair (ADR-0063); equality and label postings stay eager.

Error handling​

  • Parse errors — syntax, unexpected tokens.
  • Semantic / type errors — undefined variables, bad coercions.
  • Conflicts — overlapping writers at WAL append.
  • Constraint violations — uniqueness, existence, type, node/relationship key.
  • Capacity — optional logical memory limit on growing writes.

Errors are Result::Err with a message shown as Error: <message>.
