In about ten minutes, an agent goes from no relate at all to a small graph it has read, rehearsed a change on, changed for real, and served to itself over MCP, with every step checked. An agent can follow the same steps from the markdown twin at `https://relatedb.ai/docs/get-started/agent-quickstart.md`; the prompt to paste into an agent is the Agent tab on the [install page](/docs/get-started/install). A person can follow the same steps at a terminal.

## Prerequisites

- A shell on macOS or Linux (amd64 or arm64), with `curl`, `ssh-keygen` and `sha256sum` (or `shasum` on a Mac).
- An agent harness such as Claude Code, Cursor or Codex, if you want the skill and the MCP connection. Every other step works in a plain terminal.

## Install a pinned relate

First, we install one exact release and check it three ways before it runs: the signature on the release's checksum list, the release named inside that list, and the binary's own checksum.

<Install part="pinned" />

Notice that nothing runs until all three checks pass. If one fails, the downloads get deleted and the install stops there.

## Check the output format

An agent reads the :term[envelope]{id=envelope}: one JSON object per result set. Let's confirm the shape. The numbers in `timings` change from run to run:

```bash verify
relate --mode envelope "RETURN 1 AS ok"
```

```text
{"columnTypes":["INTEGER"],"columns":["ok"],"notifications":[],"planCache":"miss","rows":[{"ok":1}],"timings":{"elapsed_ms":0.38816700000000004,"execute_ms":0.248042,"lex_parse_ms":0.020832999999999997,"lower_ms":0.028915999999999997,"parse_ms":0.090625,"plan_ms":0.039958,"result_generation_ms":0.000292,"rewrite_ms":0.007042},"truncated":false}
```

The output should be that line, with the same keys in the same order; only the `timings` numbers differ. Every statement an agent runs on this page passes `--mode envelope`, except the `EXPLAIN` plan, so its output is the same in a terminal, in a pipe and under :term[agent mode]{id=agent-mode}, the defaults relate switches on when it detects an agent harness.

The envelope is one of relate's [output modes](/docs/reference/cli/output-modes). This statement runs in your browser, on the engine this page loads, and the terminal below shows it in four of those modes: `table`, `envelope`, `jsonl` and `toon`.

```cypher run name=names
UNWIND ['Ada', 'Grace', 'Noor'] AS name RETURN name
```

The terminal prints the same statement the way relate prints it, one view per mode, with the exit code. It runs on an empty database opened read-only, which is what `relate --read-only` opens. Now edit the statement, or pick a preset that fails and run it: notice that the JSON modes add an error object on stdout and the exit code becomes 6. "Run as an agent harness" plays `CLAUDECODE=1`, so a statement over 100 rows comes back cut, with a warning on stderr.

:::terminal{cell=names}
:::

## Install the skill

The skill is relate's cheat sheet for agents: the CLI, Cypher, and what to read for vectors, storage and safety. It ships inside the binary. This step installs it for Claude Code; the other names `--agent` accepts are `cursor`, `windsurf`, `copilot`, `antigravity`, `gemini-cli`, `cline`, `codex`, `pi`, `opencode` and `junie`.

```bash verify
relate skill install --agent claude-code
```

The path starts with your home directory, shown as `<home>`:

```text
installed relate skill into <home>/.claude/skills/relate
```

The skill now sits where Claude Code looks for skills. `relate skill check` reports whether an installed copy still matches the binary.

## Get a graph, with its checksum

Our graph is a small team: three people, two projects, who works on what and who knows whom. It's the same graph the other Get started tutorials build. A file you're handed gets its SHA-256 checked before it runs, so we check this one too.

:::note[A local file for now]
The example graph is not published as a download yet, so we write its seed script on the spot. The checksum step is the same one a downloaded file gets.
:::

Write the seed script, one `CREATE` statement:

```bash verify
cat > team.cypher <<'EOF'
CREATE (ada:Person {name: 'Ada', role: 'engineer'}),
       (grace:Person {name: 'Grace', role: 'engineer'}),
       (noor:Person {name: 'Noor', role: 'maintainer'}),
       (relate:Project {name: 'relate', language: 'Rust'}),
       (tck:Project {name: 'opencypher-tck', language: 'Gherkin'}),
       (ada)-[:WORKS_ON {since: 2024}]->(relate),
       (grace)-[:WORKS_ON {since: 2023}]->(relate),
       (grace)-[:WORKS_ON {since: 2022}]->(tck),
       (noor)-[:MAINTAINS]->(relate),
       (ada)-[:KNOWS]->(grace);
EOF
```

Check its checksum:

```bash verify
sha256sum team.cypher
```

```text
2d6ab96dc893a4c9e8bbf767e38e43a7fab76cd7af2440b48e3fe0eca4e15d0e  team.cypher
```

If the hash differs, the file is not the one this page describes: stop, and write it again. When it matches, run the script into a single-file :term[store]{id=store}, `team.rl`:

```bash verify
relate query --database ./team.rl --mode envelope < team.cypher
```

```text
{"columnTypes":[],"columns":[],"notifications":[],"planCache":"miss","rows":[],"timings":{"elapsed_ms":3.142916,"execute_ms":2.844709,"lex_parse_ms":0.014208,"lower_ms":0.020458,"parse_ms":0.279334,"plan_ms":0.012917,"result_generation_ms":0.000209,"rewrite_ms":0.0005},"truncated":false}
```

One envelope for the one statement: the `CREATE` returns no rows. Noor maintains relate but works on neither project yet. We're about to change that.

## Rehearse before you write

The change we want is one new `WORKS_ON` relationship: Noor starts on `opencypher-tck` in 2026. Before writing anything, we look at the graph, plan the write, and try it where it can't hurt.

### Read it read-only

`--read-only` opens the store :term[read-only]{id=read-only}: relate never writes it or checkpoints it, and every write fails.

```bash verify
relate --database ./team.rl --read-only --mode envelope "MATCH (p:Person)-[w:WORKS_ON]->(j:Project) RETURN p.name AS person, j.name AS project ORDER BY person, project"
```

```text
{"columnTypes":["STRING","STRING"],"columns":["person","project"],"notifications":[],"planCache":"miss","rows":[{"person":"Ada","project":"relate"},{"person":"Grace","project":"opencypher-tck"},{"person":"Grace","project":"relate"}],"timings":{"elapsed_ms":0.595166,"execute_ms":0.412,"lex_parse_ms":0.031167,"lower_ms":0.044542,"parse_ms":0.115625,"plan_ms":0.059417,"result_generation_ms":0.000209,"rewrite_ms":0.008457999999999999},"truncated":false}
```

Three `WORKS_ON` relationships, and none of them is Noor's.

### Plan the write with EXPLAIN

`EXPLAIN` plans a statement without running it, so it works on a read-only open even for a write. The values go in as `$parameters`, bound with `--param`:

```bash verify
relate --database ./team.rl --read-only --mode table --param name=Noor --param project=opencypher-tck 'EXPLAIN MATCH (p:Person {name: $name}), (j:Project {name: $project}) MERGE (p)-[w:WORKS_ON]->(j) SET w.since = 2026 RETURN p.name AS person, j.name AS project'
```

```text

| Operator         | Id | Details                 | Warnings                                |
+------------------+----+-------------------------+-----------------------------------------+

| | + SetProperty  | 1  | 1 item(s)               | -                                       |
+------------------+----+-------------------------+-----------------------------------------+
| | | + Merge      | 2  | (p)-[w:WORKS_ON]->(j)   | -                                       |
```

Notice the notifications: each names the index that would make a lookup cheaper, with the statement to create it. Five nodes don't need one. This step uses `--mode table` because a plan reads better as a table; the envelope carries the same plan as JSON.

### Turn on safe mode

`--safe` refuses statement shapes agents commonly get wrong, such as a read with no `LIMIT`:

```bash verify
relate --database ./team.rl --read-only --safe --mode envelope "MATCH (p:Person) RETURN p.name AS name"
```

The message goes to stderr, the error object to stdout:

```text
syntax error: SafeModeViolation: This statement is not allowed in safe mode: an unbounded read (`MATCH … RETURN` or `MATCH … WITH` without `LIMIT`). Safe mode refuses shapes an agent commonly gets wrong — add `LIMIT <n>`, or return an aggregate such as `count(*)`, so the read has a bounded result. This is a policy, not a database limit; reopen without --safe to allow it.
{"error":{"code":"validation_error","exit_code":6,"kind":"syntax","message":"syntax error: SafeModeViolation: This statement is not allowed in safe mode: an unbounded read (`MATCH … RETURN` or `MATCH … WITH` without `LIMIT`). Safe mode refuses shapes an agent commonly gets wrong — add `LIMIT <n>`, or return an aggregate such as `count(*)`, so the read has a bounded result. This is a policy, not a database limit; reopen without --safe to allow it.","retryable":false}}
```

With a `LIMIT`, the same read goes through:

```bash verify
relate --database ./team.rl --read-only --safe --mode envelope "MATCH (p:Person) RETURN p.name AS name ORDER BY name LIMIT 3"
```

```text
{"columnTypes":["STRING"],"columns":["name"],"notifications":[],"planCache":"miss","rows":[{"name":"Ada"},{"name":"Grace"},{"name":"Noor"}],"timings":{"elapsed_ms":0.42925,"execute_ms":0.24854199999999999,"lex_parse_ms":0.028541,"lower_ms":0.042416999999999996,"parse_ms":0.11758300000000001,"plan_ms":0.053583,"result_generation_ms":0.000375,"rewrite_ms":0.007916},"truncated":false}
```

## Read an error and its exit code

Let's make a mistake on purpose: a statement that uses `$name` without binding it. A person at a terminal reads the message and the :term[exit code]{id=exit-code}; an agent reads the error object as well, and branches on its fields.

::::agentic
:::human[At a terminal]
```bash verify
relate --database ./team.rl --read-only --mode table 'MATCH (p:Person {name: $name}) RETURN p.role AS role'
echo "exit=$?"
```

```text
semantic error: ParameterMissing: Expected parameter(s): name
exit=6
```

The message names the missing parameter, and exit code 6 means relate rejected the statement before it ran. The [errors reference](/docs/reference/errors#engine-parameter-missing) lists the message with its remedy. The fix is the missing `--param`:

```bash verify
relate --database ./team.rl --read-only --mode table --param name=Noor 'MATCH (p:Person {name: $name}) RETURN p.role AS role'
```

```text
+--------------+
| role         |
+--------------+
| "maintainer" |
+--------------+
```
:::
:::agent[From an agent]
```bash verify
relate --database ./team.rl --read-only --mode envelope 'MATCH (p:Person {name: $name}) RETURN p.role AS role'
echo "exit=$?"
```

```text
semantic error: ParameterMissing: Expected parameter(s): name
{"error":{"code":"validation_error","exit_code":6,"kind":"semantic","message":"semantic error: ParameterMissing: Expected parameter(s): name","retryable":false}}
exit=6
```

The first line is stderr; the error object is stdout. Its fields are the ones to branch on:

| Field | This error | Meaning |
| --- | --- | --- |
| `code` | `validation_error` | The class; the same class always has the same :term[exit code]{id=exit-code} |
| `exit_code` | `6` | The process exit code: the statement was rejected before it ran |
| `kind` | `semantic` | The engine's error variant |
| `retryable` | `false` | Running the same statement again cannot succeed; only a write-write conflict is retryable |
| `message` | `semantic error: ParameterMissing: …` | The text on stderr, which the [errors reference](/docs/reference/errors#engine-parameter-missing) lists with its remedy |

The fix is the missing `--param`:

```bash verify
relate --database ./team.rl --read-only --mode envelope --param name=Noor 'MATCH (p:Person {name: $name}) RETURN p.role AS role'
```

```text
{"columnTypes":["STRING"],"columns":["role"],"notifications":[],"planCache":"miss","rows":[{"role":"maintainer"}],"timings":{"elapsed_ms":0.586875,"execute_ms":0.401916,"lex_parse_ms":0.031958999999999994,"lower_ms":0.043083,"parse_ms":0.118791,"plan_ms":0.057125,"result_generation_ms":0.00020800000000000001,"rewrite_ms":0.007917},"truncated":false}
```
:::
::::

Noor is a maintainer.

## Open the MCP surface read-only

The last step serves the store to an agent harness over MCP, on stdio, read-only. For Claude Code, a person adds the server with one command. An agent writes the same server into the repository's `.mcp.json` instead, and Claude Code asks the person before it uses a server from that file.

::::agentic
:::human[At a terminal]
```bash
claude mcp add relate -- relate serve --mcp stdio --database ./team.rl --read-only
```

To allow writes, remove `--read-only`.
:::
:::agent[From an agent]
The entry goes in `.mcp.json` at the project root, which can be committed with the repository:

```json title=".mcp.json"
{
  "mcpServers": {
    "relate": {
      "command": "relate",
      "args": ["serve", "--mcp", "stdio", "--database", "./team.rl", "--read-only"]
    }
  }
}
```

To allow writes, remove `"--read-only"` from `args`.
:::
::::

Opened read-only, the server lists two tools, `read_cypher` and `get_schema`; `write_cypher` is listed only when the store is writable. A write sent to `read_cypher` comes back as a tool error, `Only MATCH queries are allowed for read-query`, and the store is unchanged.

:::tip[No network?]
Everything an agent needs to keep going is already on the machine. `relate agent-context` prints the command reference of the installed binary, and `relate agent-context <command>` adds one command's detail. `relate --help` and `relate <command> --help` print the flags. The skill's files sit in the agent's skills folder (for Claude Code, `<home>/.claude/skills/relate/SKILL.md`), and `relate skill list` prints where they are for each agent.
:::
